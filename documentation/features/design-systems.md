# Design systems

**What it is:** A design system is its own item in the Designs folder: colours, type, spacing, corner radii, shadows, layers, sizes, components, notes on how to use each, and brand files. The user reviews it, marks it Ready, and from then on designs can start from it. Plain files, so the chat agent can read and write them.

Pieces, each with its own page:
- This page: what a system is, how one is made from the New design system sheet, and what the list shows.
- [Brand files](design-system-brand-files.md): fonts, logos and documents, and the rules the service holds them to.
- [Hand edits](design-system-hand-edits.md): changing a value or a note by hand.
- [Re-sync](design-system-resync.md): bringing token values up to date with the code a system was read from.
- [Homes and adoption](design-system-homes.md): internal and repo-backed systems, how the agent's BUILD.json is checked, and why a repo system is read-only here.
- [Proposals](design-system-proposals.md): what the agent proposes before it changes a repo, the checks and preview, the approval it stamps, and what landed.
- [The list and the sheet on screen](../pages/design-systems.md).

## Where a system lives
`<Designs folder>/_systems/<id>/`: `system.json` (the structured part), tokens, the overview and notes, `assets/` and `sources/`, and a hidden `.chamber/` for what Design Chamber itself records (review state, revision, where values came from). The list never shows a system among the designs, counts it as one, or offers it in Work Status.

An **internal** system lives there only. A **repo-backed** system is read from a project's repo (made with the `/design-system` command in chat, or registered from the sheet as it is, see below); its rows say **Repo · shop**. Everything else the sheet makes is internal.

## Making one (the New design system sheet)
Steps from the list to a system with an agent working on it:

1. **New design system** (or **From code…**, **From brand files…**, **Describe…** on the empty list): 1 step.
2. Name it and tick what to start from: 1 to 3 steps.
3. Fill each ticked source: choose a project (the scan starts by itself), drop or choose files, or type a description.
4. **Make design system**: 1 step. Everything that can be wrong is said then, beside the field.

What happens on **Make design system**, in order:

1. `POST /systems` creates the Draft with what was gathered: the code scan's values the service is sure of and the ticked font and logo files, the description and preset, and a note that brand files follow. Nothing was written before this. If it fails, the sheet keeps everything and says why.
2. Each brand file is read in the sheet and sent as base64 pieces (`POST /uploads` with `encoding: "base64"`, at most 60 000 characters a piece, one file at a time), then recorded with `POST /systems/:id/assets`. A folder goes through `POST /systems/:id/assets/from-folder`. A file the service refuses (a renamed file whose contents don't match its type, a clash with the limits) is kept in the result and never stops the rest.
3. `POST /systems/:id/prompt` with `purpose: "make"` returns the request for the agent and the chip that names the system. The request tells the agent the system's folder, what to write (overview, usage notes, component inventory, anything Design Chamber couldn't parse), the sources, and to change nothing in the project.
4. Delivery: **New chat** starts a chat in the project that was scanned (else the current project) with the chip attached; **Current chat** attaches the chip and puts the request in the composer. The system remembers the chat (`PATCH /systems/:id` with `sessionId`); a failure to remember it never undoes a request that was already sent.

If step 3 or 4 fails the system still exists as a Draft with what was gathered, and the result offers **Try again** (steps 3 and 4 only: no second system, no second upload) and **Copy request**.

## The code scan the sheet starts
`POST /system-scans { directory }` starts a bounded, read-only scan; the sheet polls `GET /system-scans/:scanId` about twice a second and stops it with `DELETE` on **Cancel scan**, on choosing another folder and when the sheet closes. Only counts and paths travel to the sheet: the values stay in the service until the system is made from that scan. The project is only read. Secret files and anything a link leads out of the project are never opened.

## Starting from an existing system (Phase 2.6)
Many projects already have a design system: a page at `/design-system`, docs, components, token files. Design Chamber can find it, read what it can parse from it, and point the agent at the rest. It never fetches a web address and never writes the project.

**What every scan now says.** A scan's summary counts the files it actually opened (`read`, which is what "Files read (N)" shows, not only the files that held values) and what it saw but never parses (`missed`: pages, component files and themes written in code). Design Chamber reads CSS and token JSON; the rest is left for the agent.

**Finding candidates.** A scan of a whole project also lists up to 10 folders that look like an existing system (`candidates`, with "and N more" past that). It works from the scan's own file list and token counts only: no second walk, no extra file opened, so `node_modules`, build output, dot folders, links and secret files are never considered. A folder qualifies when it holds Design Chamber's file contract (`system.json` and `tokens.css`), a design-system page (`app/design-system/page.tsx`, `public/design-system/index.html`, `src/pages/design-system.tsx`), when it is named like one (`design-system`, `style-guide`, `ui-kit`), when it holds `DESIGN.md` or `design-system*.md`, or when it has docs and token files together. A lone token file or a lone brand note does not. Each candidate carries its path, what marks it (contract, page, tokens, docs, components, theme), counts, whether it is strong enough for the sheet's nudge (contract, page or a system-named folder), and the system already made from it ("Already in Design Chamber as Speak UI"). Only a folder with `system.json` is ever marked as the contract.

**Reading one folder.** `POST /system-scans { directory, location }` scans only that folder. The location may be relative to the project or a full path, with either slash. It is refused before anything is touched when it looks like a web address ("Use the folder on this machine, not a web address.") or a network share from a local project; then it must exist, be a folder, not be the Designs folder or inside it, and lie inside the project compared as real paths, so a link inside the project that leads out is refused ("Pick a folder inside shop."). The answer's `location` lists the page, docs and component files found there (at most 20 of each) and, when the folder holds `system.json`, whether the contract is complete or what is missing. A complete one is read whole into the scan's memory, exactly as a snapshot is read, ready for registering.

**Make a new system from it.** `POST /systems` with that scan makes an internal Draft as from code. The folder is checked again first ("That folder is gone. Pick another location." if it went). The system records the folder as its code source, so a later re-sync reads the same place, plus the project and the files found there. The request to the agent names the project (not the folder) in "Don't change anything in…", says to start from the system in that folder, lists the files to read first and says to reconcile to what is there rather than invent a parallel system. When the request is too long the file lists shrink first (20, then 5, then none). A re-sync that moves the code source outside the project turns it into a plain code source.

**Register it as it is.** `POST /systems/register { scanId, name }` takes a done location scan whose folder holds a complete contract. It makes a repo-backed Draft that is read-only here, with its first snapshot from the scan's own read (re-hashed, never read again) and recorded as the user's. There is no ticket, no BUILD.json, no build record and no request to the agent. The living page goes to `index.html` in that folder, or `living-page.html` when `index.html` is taken; with both taken it is refused. P25's repo-home checks run inside the create step (another system in the same folder is named in the refusal), the name must be free, and a failure after the folder was made moves it to the trash so nothing half-registered stays. A registered system is not "being built"; Stop and "pick up the build" are refused because there was no chat build; re-sync, the living-page request and delete work as for any repo-backed system. The folder's own page is not adopted as the living page: when `index.html` is taken the living page path is `living-page.html`, and until the agent writes one the system shows the missing-page ask like any repo home without a page.

**The builder flow.** In a `/design-system` chat the agent may record the system it started from in BUILD.json as `"existing": { "folder": "design-system" }` (`"."` for the project root). On adoption it must be a folder inside the chat's project; otherwise it is ignored and the system page says "The existing system must be a folder inside the project this chat is in, so Design Chamber ignored it." The build is adopted either way. The adoption scan fills in the files found there and lists the candidates in `.chamber/scan.json` for round two.

## The sheet's Existing design system start (Phase 2.6)
The New design system sheet has four starts: Project code, Brand files, A description and **Existing design system**. Project code and Existing design system exclude each other (ticking one unticks the other; the chosen project stays). Ticking Existing design system also unticks an empty A description with no preset, so a start stays within the step budget. At laptop width the sheet is three columns (what to start from / where the system lives / what Design Chamber read and what should happen with it); at the rail's width it is one column in that order. The approved canvas is `Designs/phase-2-6-library-ui`, screen `system-sheet-existing`.

**Finding it.** With Existing design system ticked, the sheet reads the chosen project (the same scan Project code uses) and says "Looking for a design system in <project>…" with Cancel. When it settles, **Looks like a design system** lists up to ten places, ranked, each with its path, what marks it ("system.json, page, tokens, 3 docs"), its counts ("24 colours · 29 tokens") or "Nothing to parse", and "and N more. Type a folder below to use another." past ten. A folder holding Design Chamber's file contract carries a **Complete** badge; a place already registered says "Already in Design Chamber as <name>" with an **Open** button that opens that system's page. With nothing found: "No existing design system found in this project. Point at a folder yourself, or start from the code." A failed project scan keeps its sentence and offers Try again.

**Reading one folder.** Picking a candidate fills **Where does it live?** and reads it in one action; the field also takes a typed path (Enter or **Read this folder**). The helper says "A folder inside <project>. Design Chamber only reads it." A refusal (a web address, a path outside the project, a folder that isn't there) shows the service's sentence under the field and keeps what was typed. While the folder is read, the third column says what it found, scoped to the folder: the found sentence, what Design Chamber never parses ("… It saw 1 page and 14 component files."), what is left for the agent (its page paths, doc and component counts), skipped files by name, **Files read (N)** with the real read count (the files with values listed first, then "and K more with no values"), and any font or logo found, ticked to copy in with the licence note. A folder with no token files says so and offers Make anyway: the agent can still read its page and docs.

**What should happen with it.** A complete contract offers two choices: **Register it as it is**, preselected and marked **Recommended** ("… Nothing is written to <project> and the agent isn't asked."), and **Make a new system from it** beside it. The footer's primary follows the choice: **Register design system** or **Make design system**. While Register is chosen, **Agent works in** is disabled with its reason: "Only needed when the agent writes the system. Registering it sends no request." An incomplete contract shows no choice, only the line naming what is missing ("This folder has a system.json but tokens.css is missing or holds no token values, so it can't be registered as it is. Make a new system from it instead."; the service names one gap for an absent tokens.css and for one with no custom property, so the line says both; if system.json goes missing between the walk and the read it says "While the folder was read, system.json went missing" and offers to read again); the project root gets its own line (a registered system needs a folder). The footer keeps the promise "Your repository stays exactly as it is." whenever Existing design system is ticked.

**The nudge.** With Project code ticked and a strong candidate found (a contract, a page or a system-named folder), a banner over the scan says "This project already has a design system in <path>/. Start from it instead?" with **Start from it** (ticks Existing design system, fills the location, reads it; the name and everything else typed stays) and **Dismiss**. Once per sheet session; it never blocks Make.

**Registering.** One call (`POST /systems/register`), no agent request, no chat. Success: the toast "Registered <name> from <project>. Review it, then mark it ready.", the sheet closes and the system's page opens on its read-only repo panel as a Draft. A refusal (name taken, overlap, no place for the living page, the folder gone or changed) shows its sentence above the buttons and keeps everything; nothing half-made stays. Making from a location goes through the same Make path as Project code, with the location's scan and its ticked assets; the agent's chat is the project the folder sits in.

**Steps** (budget ≤ 6): New design system (1) → tick Existing design system (2) → pick a candidate (3) → Register design system (4); an optional name edit is 5. The project is preselected and its name suggested, so nothing needs typing on the happy path.

## What the list shows
Each summary also carries when the system was made and up to six of its light colour values (brand colours first, each a valid colour, never a `var()` reference) for the library's tiles; they are system content, painted only after the guest checks them again. Each row: the plate (the system's own colours, Aa and a thin strip), name, **Draft** or **Ready**, where it lives, at most two badges by priority (**Being built**, **Changes to review**, **Default**, **Pinned for shop**, the living page's state), anything beyond two folded into "+N", a shared-repo line, what it was made from, who uses it and when it changed. **Used by 4 designs** is a link: it closes the list and shows the library filtered to that system (scope All designs, tab All, no search), one step from a system to its designs; a system nobody uses says "Not used yet" as plain words. The same row is the Design systems list on both surfaces; the page's library draws a system as a tile in All and Systems (the rail's library lists designs only, with a pinned entry to this list) ([Library: design systems in the library](../pages/library.md#design-systems-in-the-library)). Draft means no design can start from it yet; Ready means it can. The priority and folding rules are pure and tested (`src/ui/model/systems-model.ts`, `test/ui/systems-list-model.test.ts`).

**Make default** writes the default into settings (`PUT /settings` with `systemDefault`); only a Ready system can be the default, and **Remove as default** goes back to asking each time. **Delete…** moves the system to the Designs folder's trash, clears the default and pins that named it, and says so. Designs that already use it keep their copy.

## Rules the screens hold
- Nothing is written before the footer button (**Make design system** or **Register design system**); input is kept on every failure.
- Register it as it is writes nothing to the project and asks the agent nothing; the agent field is disabled with its reason while it is chosen.
- One filled button per view. A description or a preset is enough to make one from a description; a code source needs a finished scan; a brand source needs a file or a folder; an existing source needs a read location.
- Names: 1 to 60 characters, no line breaks or tabs, unique ignoring case.
- Files by picking or dropping work inside the sandboxed frame (spike SP-1); **Add from a folder…** is the way for a folder.
- Text from a system, a scan or a file name is always shown as text, never as markup.

## Board layout hints
The agent that writes a system says how the specimen board lays out each entry; Design Chamber still draws the board and picks from a closed set. In `system.json`, a component, note, pattern or brand entry can carry `"layout"`, and a top-level `"layout"` object gives section defaults, for example `{ "components": "compact", "colours": "table" }`. An entry's own value wins, then its section's, then `card`.

| Layout | Looks like | For |
|---|---|---|
| `card` (default) | today's cards: components in columns at least 600 px wide, a too-wide preview takes the full width | most entries |
| `compact` | narrower columns (about 280 px) and smaller token swatches | buttons, badges, pills, avatars |
| `full` | one entry per row across the whole board | tables, navigation, toolbars, page headers |
| `table` | aligned rows with a header; stacks below 760 px of section width | long lists read row by row |

Components, notes, patterns and brand entries take all four. The notes' section default is written `"notes"` (Design Chamber also reads `"overview"`, which wins when both are set). Colours, spacing, radius, shadows and sizes take a section default of card, compact or table. Typography, layers and assets take none. An unknown value, or one a section doesn't take, is ignored (that entry uses the default) and the check warns, saying for each one what its place takes; it never makes an entry unreadable.

Rules the board holds:
- **Order is the agent's.** Neighbouring entries with the same layout form one group; nothing is reordered.
- **Light and dark grounds stack** in every layout, so a preview always has the card's full width.
- **Tables fit their content.** A token table's Token column is as wide as its longest name and value (up to 420 px), so the note sits beside it. A text table (notes, patterns, brand) drops its Note column when no entry in it has a note. Guidance, overview and note text stop at about 90 characters a line, whatever the layout's width, on the board and the living page.
- **Presentation only.** A layout change doesn't reset a section's "Looks good" review. It is still a change to `system.json`, so it is a new revision: linked designs see that a newer system exists, and a repo's living page reads out of date until it is regenerated.
- **Markdown in every layout.** Overview, note, pattern and brand bodies render as markdown (headings, lists, quotes, code, tables) the same way in card, compact, full and table layouts, on the board and in the living page's narrower vocabulary; a note's own leading title is dropped in table rows as on its card.
- **The living page follows the hints too**, with the same groups and table rows (its examples are pictures that scale down, so it needs no measuring).
- The panel has no layout control: the brief makes this the agent's job.

The visual system check draws the board with these hints and says when a hint is too small for an entry ("set to compact but needed the full width. Set its layout to full.") ([Design checks: drawing the board](design-checks.md#drawing-the-board)).

Code: `src/shared/system-json.ts` (`readItemLayout`, `readSectionLayouts`, `effectiveLayout`), `src/service/systems/specimen-html.ts` (runs and table markup), `src/service/systems/board-html.ts` (board CSS and script), `src/service/systems/living-html.ts` (living page CSS). Tests: `test/shared/system-json.test.ts`, `test/service/systems/specimen-html.test.ts`, `board-html.test.ts`, and the Chrome layout test `board-layout-e2e.test.ts`.

## Depth, live examples and colour pairs
A system can say how complete it means to be and show more of itself on the board (spec: `documentation/specs/system-builder-depth.md` §4.3, §4.4). Everything here is optional in `system.json`; a system written before it reads exactly as it did, and no review resets.

- **`depth`**: `tokens`, `core` or `full`. It drives the completeness check ([Design checks](design-checks.md)). Anything else is one problem on `depth` and the check is off.
- **`outOfScope`**: checklist topic ids the user agreed the system won't cover (the agent asks first, and an interview answer such as "No motion" counts), for example `["motion", "marketing"]`. Those topics stop counting as gaps. Only ids from the checklist are read (up to 40); unknown ones are named in one problem. Neither `depth` nor `outOfScope` changes a section's review.
- **Component sizes.** `components[].sizes` lists up to 10 size names, like `variants` and `states`. The board shows them on the card ("Sizes: sm, md, lg").
- **More pattern and brand kinds.** Patterns also take `navigation`, `overlay`, `forms`, `data-display`, `feedback`, `states`, `page`, `responsive`, `motion` and `accessibility`. Brand entries also take `colour`, `social` and `email`.
- **Live examples on patterns and brand entries.** `"example": "patterns/<id>.html"` (or `brand/<id>.html`) draws a live example exactly like a component's: bundled on its own, inert in a template, attached to a shadow root inside the board's sandboxed frame, light and dark grounds stacked. It sits under the entry's note and above its guidance, in cards and table rows, and a too-wide example takes the whole row. A missing or too large example says "This example couldn't be shown." A pattern and a component may share an id. A changed example resets that section's review, as a changed component example does. Copies of the system for a design carry the examples as agent reference, and a repo snapshot reads them with the example cap.
- **Colour pairs.** `pairs` lists what colour sits on what: `{ "fg": "--fg", "bg": "--bg", "use": "text" }`, where `use` is `text` (needs 4.5:1), `large` or `ui` (3:1), with an optional note. Both must be colour tokens the system sets. Every `--x-fg` or `--on-x` colour whose `--x` exists becomes a pair on its own, labelled "Found from the token names". Up to 60 pairs in all. The board shows a **Pairs** block at the end of Colours: "Aa Text" in the pair's colours on the light ground, and on the dark ground with the dark values when the system has any, each with its ratio (rounded down, so 4.499 never reads 4.50) or "Measured by the check" when the value isn't a plain hex or rgb colour. Pairs follow the Colours layout (card, compact or table). Declared pairs count toward the Colours review; found ones don't (they come from tokens already counted).
- **Recorded in BUILD.json too.** The agent writes the depth answer as `depth` and the platforms answer as `platforms` (a list of the choice ids) in BUILD.json, and copies `depth` into `system.json`, since the check reads only system.json. A wrong value in BUILD.json is one problem on that field; the build is still adopted.
- **The living page** shows the same: pattern and brand examples as pictures, the Pairs block, all inside its allowlist. Pictures are cached by their content, so a pattern and a component with the same example share one.

Code: `src/shared/system-json.ts` (the reader and fingerprints), `src/shared/system-checklist.ts` (the topic ids), `src/shared/pair-contrast.ts` (pair ratios, shared with the panel), `src/service/systems/specimen-html.ts`, `board-html.ts`, `board-assemble.ts`, `living-html.ts`, `living-examples.ts`. Tests: `test/shared/system-json.test.ts` (the "builder depth contract" block, with the 0.7.0 detail of an old system in `test/shared/fixtures/`), `test/service/systems/builder-depth-board.test.ts`.

## Motion
Durations and easings have their own section, **Motion**, under Foundations after Shadows (spec: `documentation/specs/system-builder-depth.md` §4.6, T10a).

- **Which tokens.** A token named `--duration-*`, `--ease-*` or `--motion-*` whose value is a time, an easing or a formula, or any token with `"section": "motion"` in `system.json`. A motion name holding something else (`--motion-distance: 8px`) is sorted as before.
- **Older systems.** The Phase 1 rules told agents to leave these tokens in `other`, so a recorded `"section": "other"` on such a token now reads as Motion; nothing in the files changes, and its note stays with it. The tokens leave the Sizes section, so a system that had them shows Sizes as not reviewed once, and a Ready one shows "Changes to review" for Sizes. That is accepted (spec open question 8): one re-review instead of a second fingerprint rule.
- **Values.** A time in `ms` or `s` from 0 to 10 000 ms, or an easing: `linear`, `ease`, `ease-in`, `ease-out`, `ease-in-out`, `cubic-bezier(x1, y1, x2, y2)` with both x from 0 to 1, or `steps(n)` / `steps(n, start|end)` with n from 1 to 100. `cubic-bezier()` and `steps()` are accepted in this section only. Anything else is shown as unreadable with that shape, and a hand edit is refused with it. A project scan keeps these values too.
- **Layouts.** Motion takes card, compact or table, like the other token sections.
- **Reviews and Ready.** A system marked Ready before Motion existed has no Motion entry in its Ready record, so the new section alone never shows "Changes to review". Motion starts not reviewed like any section, so marking a draft Ready now lists the Motion section as unreviewed, even when it is empty.
- **Checks.** The `motion` checklist topic is met by one time and one easing in the section, or (as before) by a `--duration-*` and an `--ease-*` token. `system-motion-no-reduced` warns when an example moves without a reduced-motion rule ([Design checks](design-checks.md)).
- **Not yet.** The board, the living page and the panel don't draw Motion yet (T10b, T10c); its tokens are read, checked and reviewed.

Code: `src/shared/token-edit.ts` (`classifyToken`, `validateTokenValue`, `resolveTokenSection`, `motionValueKind`), `src/shared/system-json.ts` (`TOKEN_SECTIONS`, `LAYOUTS_OF_SECTION`), `src/shared/system-checklist.ts`. Tests: `test/shared/system-motion.test.ts`.

## Using a system from a design
A design shows its system as a chip in the viewer, with an update banner, a review sheet, Change… and Undo ([Viewer: a design's system](../pages/viewer.md)). Rows and cards in the designs list carry a **System updated** badge when the system has a newer revision than the design's copy, and a **chip** naming the system: one click opens it (Draft is marked, a deleted system reads "(deleted)" and says so when pressed). Defaults and project pins live in Settings, and the New design dialog preselects from them ([Settings: Design systems](../pages/settings.md)).

### Use the project (the default for every project)
A new design for a project picks its system in this order: the New dialog's pick, then the project's row in Settings, then **Use the project**, then your default.

- **Use the project** is what a project gets with nothing set. If the project has its own Ready system, the design links it (copy-on-link, as for any system). A project's own system is one kept in its repo (built there with `/design-system` or registered as it is) or made from its code, including a repo inside the project and a project opened in a package of the repo; with two, the closest wins, then a repo one, then the newest.
- **No own system, but design files.** When the project scan finds a design doc, a token or theme file, or a design section in AGENTS.md or CLAUDE.md, no system is linked and the design **follows the project** (`systemDecision: "project"` in its state). The agent is told to read those files, the project's component and screen folders and its stories, and to build the design the way the project already looks. The chip reads **Follows the project**. A thin project (only a Tailwind config, say) still counts: it wins over a global default system, which stays one click away on the chip (owner decision, 2026-11-27).
- **A project folder that can't be read** (or a scan that times out) follows the project too; the agent is told to look itself.
- **Nothing found.** Your default decides, as before (a system, none, or ask).
- **Use my default** in Settings skips the project rung; **No design system** links nothing, and the agent still follows the project's own files (owner decision). A system picked for the project wins over the project's own one, and Settings says so.
- A design made before this keeps its decision; nothing is re-linked. If a link of the project's own system is refused at creation (it changed a moment ago), the design follows the project instead.
- Agents in a project with its own Ready system and no pin also get the line "Designs for this project use the design system "<name>" in Design Chamber." ([Agent instructions](agent-instructions.md)).
- Code: `src/shared/systems.ts` (`effectiveSystemChoice`, `projectSystemOf`, `choiceSystemsOf`), `src/service/routes/chat.ts` (`POST /chip`), `src/service/agent-system.ts`. Spec: `documentation/specs/use-the-project-and-native-agent.md` §1. Code: `src/ui/components/system-chip.ts`, `src/ui/model/design-system-model.ts`.

## Asking in chat (the SystemAsk block)
A `/design-system` chat asks its questions in place, as one chat block with three views (spec §8.12). It sits in the chat's reply and answers the chat with one message.

- **Round one, "Before I read the code" (Round 1 of 2).** Where the system lives, whether to fix the code or only describe it, which parts to cover (checkboxes), how complete it should be (**Product core**, recommended; Full system; Tokens only), and dark mode. The recommended answer is bold and already picked. **Go with these** sends the picks. With no project folder open in the chat, home and mode are hidden and a line says the system will live in Design Chamber and the code stays untouched.
- **Round two, "A few calls from the code" (Round 2 of 2).** Only the calls the agent found, each with its fixed options and "From the agent:" lines for why and what it proposes. Besides status colours, greys, who can open the living page, typography and dark values, the agent can raise platforms (laptop and phone, phone first, laptop only), navigation, overlays (sheets on phone, modals on laptop), motion, spacing and radius scales (fix mode only) and brand colour (a marketing palette apart from the product accent). Each says in the interview file what finding raises it. Picking **Custom** points to the note. A call the block can't show is counted in a line ("1 question couldn't be shown; answer it in the chat.").
- **The diff.** The header names the system (read from the service, never from the block's text). Each part (System files, Token fixes, Docs, Living page) has a switch, on by default, with its file count. Files open to their patch as plain text; unlisted use rewrites are summed up ("214 uses in 38 files. Listed in the chat."). **Preview living page** and **Open the board** open Design Chamber in the rail. **Approve** reads "Approve all 4 parts" or "Approve 3 of 4 parts" and is off, with the reason, when no part is on or the proposal has problems. **Decline** swaps the footer to **Describe only instead** (fix mode only), **Stop** and **Back**. Stop removes the draft first and then tells the chat; **Undo** brings it back for a few minutes. A 409 shows its own sentence and sends nothing.
- **Both rounds have their own note box.** A note alone never counts as approval.
- **Read-only states.** Superseded, rewritten, unknown, unreadable and expired proposals or tickets show a sentence and no buttons. An answered block shows what was picked. If the host won't take the answer, the choices stay and **Copy my answer** appears; any other refusal says "Couldn't send your answer. Type it in the chat instead." and keeps the form.
- **Fresh.** The block rereads on window focus and every 5 seconds while it is visible and unanswered.
